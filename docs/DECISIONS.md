## D-001 — Keep the engine, isolate tree generation (2026-10-25, planning)
Decision: The engine stays as is (cleanup only). Tree generation moves into a pure `treegen` static library with no dependency on `Engine/`/`GraphicEngine/`; legacy `Lindenmayer*` classes become adapters, then are deleted (T07).
Why: Owner wants to keep the current engine now but be able to split the generator out later (e.g. as a Blender/Godot/Unity plugin core, CLI or WASM tool).
Consequences: Boundary enforced by a CTest include-grep (T03) and by building `treegen` as its own CMake target with a minimal include path.

## D-002 — Test framework: doctest via FetchContent (2026-10-25, planning)
Decision: Use doctest (single header, pinned tag `v2.4.11`) fetched by CMake `FetchContent`, behind option `ESTREE_BUILD_TESTS` (default ON). T01 may deviate if offline builds prove problematic; record it here.
Why: Smallest dependency, fast compile, works with CTest.
Consequences: Network needed on first configure; T11 caches it in CI.

## D-003 — Library layout and naming (2026-10-25, planning)
Decision: Directory `ESEngine/TreeGen/` (headers in `include/treegen/`, sources in `src/`), CMake target `treegen`, namespace `treegen`, include as `#include <treegen/Xxx.h>`. Tests in `tests/`, tools in `tools/`.
Why: Self-contained layout that can be lifted out of the repo unchanged.
Consequences: The engine's include root stays `ESEngine/`; adapters add `ESEngine/TreeGen/include` via `target_link_libraries(ESTree PRIVATE treegen)`.

## D-004 — Rule-file format v1 is frozen; extensions are additive (2026-10-25, planning)
Decision: Existing JSON (`parameters`, `axiom`, `rules[{symbol,production,probability,initialDepth}]`) and `.l` formats keep working unchanged. New optional keys (`seed`, `maxModules`, later `condition`) are additive.
Why: 20+ shipped rule files and the thesis examples must keep working.
Consequences: Loader tests iterate over every file in `Resources/LindenmayerRules`.

## D-005 — Build: CMake ≥ 3.21, presets, explicit vc140 Boost libs (2026-10-25, T00)
Decision: Root `cmake_minimum_required(3.21)` (presets schema v3). Presets pass `CMAKE_POLICY_VERSION_MINIMUM=3.5` so CMake 4.x accepts vendored projects (Bullet 2.4.3, FreeType 2.8) without editing `Vendor/`. Boost is configured through `BOOST_LIB` (env or cache) and linked explicitly (`date_time thread chrono system atomic filesystem program_options`, `vc140` static libs) with `BOOST_ALL_NO_LIB`, because auto-link would request non-existent `vc142/vc145` names. `bcrypt` is linked on Windows for `boost::uuids`. C++17 is the project standard.
Why: Owner installed CMake 4.4.4; the bundled VS2019 CMake 3.20 cannot read schema v3 and cannot generate for VS 2026.
Consequences: Revisit when Boost is removed (T13). `Vendor/` untouched.

## D-006 — Typed component access keeps the `ComponentType` enum (2026-10-25, T10)
Decision: `GameObject::getComponentAs<T>(ComponentType)` / `getComponentsAs<T>(ComponentType)` (and the forwarding `Component::getComponentAs<T>`) are `static_cast` accessors; `Component` has a virtual destructor so Debug builds `assert(dynamic_cast<T*>(...))`. `getComponent(TYPE)` is unchanged. Casts in `ESEngine/Engine` were replaced; the ones in `ESEngine/ESTree` (scenes, console commands, `Models/`) still use C-casts.
Why: Smallest change that fits the existing enum scheme; no ECS redesign (BACKLOG).
Consequences: A wrong `T` for a type (e.g. `InstancedMesh` read as `Mesh`) now asserts in Debug instead of being silent UB. Call sites in `ESTree/` can migrate at will.

## D-007 — ASan build needs the VS 2019 Build Tools toolset on this machine (2026-10-25, T10)
Decision: `ESTREE_SANITIZE=ON` (presets `ninja-msvc-asan`, `vs2019-asan`) adds `/fsanitize=address` to ESTree, the tests and the vendored libraries. The x64 ASan runtime exists only in the VS 2019 Build Tools here (VS "18" ships the i386 runtime only), so `ninja-msvc-asan` is configured with `VCVARS64` pointing at the 2019 `vcvars64.bat`. The 14.29 ASan runtime only starts together with the 14.29 CRT DLLs (a newer `vcruntime140.dll` in System32 gives 0xC0000142), so the CRT DLLs are copied next to each executable after linking. GCC/Clang get `-fsanitize=address,undefined`.
Why: Without the copy no ASan executable runs on this machine.
Consequences: ASan executables are self-contained next to their DLLs; on a machine whose System32 CRT matches the toolset the copy is redundant but harmless.

## D-008 — CI: engine behind `ESTREE_BUILD_ENGINE`; Linux builds the engine against system Boost (2026-10-25, T11)
Decision: `ESTREE_BUILD_ENGINE` (default ON on Windows, OFF elsewhere) gates GLFW, Bullet, FreeType, the `ESTree` executable and `tests/engine`. `BOOST_LIB` is required only for an MSVC engine build; `BOOST_INCLUDEDIR` overrides the Boost header directory. Non-MSVC engine builds link system Boost (`boost_*` libs) instead of the vc140 names. Windows CI runs with the engine OFF (runners have no vc140 libs); Linux CI builds the engine ON (compile+link only) and OFF. A handful of MSVC-only constructs were made standard C++ (opaque enums with `: int`, `const T&` for temporaries, no extra qualification, `<sys/stat.h>`, `windows.h` guarded).
Why: The full engine cannot be built on a stock Windows runner until Boost is removed (T07/T13); Linux compile coverage catches non-portable code early.
Consequences: Windows CI does not compile the engine; the owner's local `ninja-msvc`/`vs2019` build remains the Windows engine check until T13.

## D-009 — treegen loaders replace the legacy params loader; loader defects #1, #3, #10-#13 fixed (2026-10-25, T03)
Decision: `treegen::loadTreeParams` (hand-written JSON/`.l` loading, no `std::regex`, no Boost) is the only loader; `LindenmayerTreeParams` is an adapter that inherits `treegen::TreeParams` and keeps `Rule`/`addRule`/`getRules`/`getAvailableRules`/`radians`. Additive API beyond the design doc: `parseTreeParamsLegacy`, `substituteParameters`. Optional keys `seed`/`maxModules` live at the JSON top level or in `parameters` (`define seed N` / `define maxModules N` in `.l`). A missing file, invalid JSON, a missing/mistyped `axiom` or `rules`, and any wrongly typed value is a `treegen::LoadError` (`<path>[:<line>]: <reason>`), which replaces the crash/UB of the old loader.
Flipped KNOWN BUG expectations (tests renamed, `KNOWN BUG:` prefix dropped; list in `tests/golden/KNOWN_BUGS.md`):
- #1 adjacent identical parameters (`F(a1,a1)` is now `F(35.000000,35.000000)`) and #3 parameter at the start of a production: custom parameters are replaced as whole words (boundary `[A-Za-z0-9]`, same class as before; also at the end of the text). The T02 example `a1F` is a different identifier and stays unreplaced; the tested start-of-text case is `a1+F`.
- #10 custom parameters are substituted into the axiom (`legacy/parametricTree2.l`); substitution now runs after the whole file is read, for the axiom and all productions.
- #11 bare-number header lines of old `.l` files (`advancedTree.l`, `testX/Y/Z.l`) are depth, initialLength, initialRadius, angle (degrees) while no axiom has been seen; `depth` defaults to 0 instead of being uninitialized.
- #12 the default angle is `radians(15)` for loaded files too (it was 15 radians), `define tropism x y z` is parsed and normalized. Visible effect: none for the 39 files that set `angle` (all 21 JSON files and 18 `.l` files); the four header-form `.l` files now use their header angle (7 or 15 degrees) instead of 15 radians.
- #13 (new) a UTF-8 BOM at the start of a `.l` file is skipped; `legacy/test.l` used to get a junk rule whose symbol was the BOM. Also: `\r` is stripped, `.l` tokens are separated by runs of spaces and tabs, values and probabilities are parsed strictly (`LoadError` instead of `atof` returning 0).
Regenerated goldens (reviewed by eye, nothing else changed; the other 37 params goldens and all other solver goldens are byte-identical): `params/legacy__advancedTree.l`, `legacy__testX.l`, `legacy__testY.l`, `legacy__testZ.l`, `legacy__parametricTree2.l`, `legacy__test.l`; solver goldens that are a function of the loaded axiom/depth: `solver/legacy__parametricTree2.l.d0..d3`, new `solver/legacy__advancedTree.l.d4`.
Why: Review Focus 2 and the "behavior-preserving except listed bug fixes" rule; the loader had to be portable (the regex-based loader loses text on libstdc++).
Consequences: Callers of `LindenmayerTreeParams(path)` can now see a `LoadError` for a malformed file (ConsoleTreeCommand does not catch it yet: T07). Trees built from the four header-form `.l` files change (they used 15 radians and defaults); needs a human look if those files matter. The solver is untouched; bugs #2, #4-#9 stay with T04.

## D-010 — treegen turtle: identity start, honored `-1`, unbalanced `]` is an error, `$` guard (2026-10-25, T05)
Decision: `treegen::interpret` (Turtle) replaces the turtle of `LindenmayerTreeInterpreter`, which becomes an adapter that replays the `Skeleton` into the unchanged `LindenmayerTreeMeshGenerator` (parents before children, same ring order, same `roll - parent.roll` alignment). Semantics are the alphabet table of `docs/architecture/overview.md`; the intentional differences from the legacy code are:
1. **Identity start quaternions.** The legacy code builds its start state with `glm::quat()`. With the pinned glm (0.9.9.8, no `GLM_FORCE_CTOR_INIT`) that is the zero quaternion `(0,0,0,0)`, not identity (verified on MSVC Debug and `/O2`). As built, rotations before the first `F` are multiplied into zero and lost, and the accumulated rotation stays zero, so `T` always sees the heading `(0,1,0)` and with the usual tropism `(0,-1,0)` bends nothing: **tropism has been a no-op in the shipped binary** (glm upgrade of 2020-04; older glm initialised `quat()` to identity). treegen starts from identity, which is what the table, the thesis and the brief's "`T` bends towards the tropism" describe. The equivalence harness proves both halves: `Turtle equivalence: as compiled, the legacy tropism T is a no-op` (the as-compiled legacy ignores `T` to 5e-7) and the identity-start reference equals treegen.
2. A literal `-1` parameter is honored (`params.empty()` instead of the `-1` sentinel; legacy `F(-1)` re-read `(`,`-`,`1` as symbols). Parameters of unknown symbols are ignored as a whole (legacy executed the `-` of `A(-1,2)` as a roll). Parameters of `[`, `]`, `$` are ignored. `X~` without a bound draws nothing.
3. `]` without a matching `[` throws `InterpretError` naming the module index (legacy: `top()` on an empty stack, UB). An unmatched `[` at the end stays allowed.
4. `$` on a heading parallel to the world axis (a freshly reset turtle) leaves the rotation unchanged; the legacy code normalised a zero vector (NaN frames). The root segment has `roll = 0` (it was uninitialised memory read for the first segment); `Segment::roll` now defaults to 0.
5. Normalisation: only the accumulated rotation is renormalised after each `F` (the legacy quaternions are never normalised and the tropism quaternion has norm < 1, so the legacy accumulated rotation shrinks along paths with many `T`). The segment frame still uses the raw local rotation, because `$` yields quaternions of norm < 1 that the shipped trees were built with. Effect, measured against the verbatim legacy math started from identity: productions without `T` are bit-identical (all 134 shipped goldens up to depth 4); productions with `T` deviate by up to 0.08 world units at depth 3 and 0.2 (ternary B) / 1.7 (ternary C) at their own depth 6; against reference-plus-normalisation treegen is bit-identical.
6. `~` randomness: `Rng(seed).derive(2)`, `uniform01() * bound`, one draw per module that reads a parameter, in module order. The adapter seeds it with `params.seed` (legacy: `time(0)`; no shipped rule file uses `~`). The adapter catches `treegen::Error` (malformed product text, unbalanced `]`), logs it and degenerates the tree to its root instead of throwing out of the render path.
Why: Review Focus 1 and 6; a library must not depend on an uninitialised-vs-zero accident; `T` and early rotations are core features of the generator.
Consequences: **Trees using `T` look different from the current binary** (the ternary rule files A-E, including scene 0's default `parametricTernaryTreeB.json`: at depth 6 branch tips move up to 6.3 units on a 13.6 high tree, they now droop towards the tropism). Trees without `T` and without rotations before their first `F` are unchanged. To reproduce the old look exactly, drop the `T` modules in the adapter before `interpret`. `legacy/parametricTree2.l` has a typo in its own rule (`[^+a)F`, lost `(`), so its products are not module strings: the legacy turtle skipped the stray characters one by one, `parseModules` rejects them, and the adapter now draws that tree (console-only, no scene uses a `legacy/` file) as its root with a logged error. Frozen legacy math with a switch for both quaternion starts: `tests/treegen/legacy_reference/` (deleted in T07).

## D-014 — treegen rewriter replaces the regex solver; solver defects #2, #4-#9 fixed (2026-10-25, T04)
Decision: `treegen::rewrite(params, {seed})` (`Rewriter.h`, `Expression.h`) is the only rewriter; `LindenmayerTreeSolver::generateTreeProduction` is `toString(rewrite(params, {seed}))` with `seed = params.seed` or, when 0, a fresh `std::random_device` value (engine trees stay varied; T07 exposes the seed). No `std::regex`, no Boost, no statics. Productions are compiled once per rule into literal modules plus `Expression`s (`+ - * /`, unary `-`/`+`, parentheses, literals, rule parameter names; standard precedence, left associative). Selection: `Rng(seed).derive(1)`, one draw per rewritten module, rule k wins when `sum(p[0..k-1]) <= u < sum(p[0..k])`, a draw past the sum keeps the module. Errors are `RewriteError`s: arity mismatch (a module must have exactly as many parameters as the rule declares), malformed production or expression (message names the rule and the offset), NaN/Inf/float overflow of a parameter (names the expression), more than `maxModules` modules.
Flipped KNOWN BUG expectations (tests renamed, `KNOWN BUG:` prefix dropped; list in `tests/golden/KNOWN_BUGS.md`): #2 adjacent identical parameters (`F(x,x)` -> `F(2.000000,2.000000)`), #4 leading minus (`F(-5*2)` -> `F(-10.000000)`), #5 negative parameter values (`l=-2`, `F(l*3)` -> `F(-6.000000)`), #6 chained operators and precedence (`F(2*3*4)` -> `F(24.000000)`, `F(1+2*3)` -> `F(7.000000)`), #7 an empty production gives the empty string, #8 regex-metacharacter symbols (`+`, `^`, `*`) can be rewritten, #9 arity mismatch is a `RewriteError`. New #14: a malformed production is a `RewriteError` instead of being copied into the output.
Compatibility: for the 34 deterministic rule files `rewrite` reproduces all solver goldens digit for digit (the golden tests compare `toString(parseModules(golden))` with `toString(rewrite(...))`: the legacy string kept literal numbers as written, `+(45)`, `ModuleString` prints `+(45.000000)`). To get the same digits the rewriter keeps the legacy numeric model: computed values are rounded to six decimals (what `std::to_string` text did between iterations), arguments that are the float nearest to a six-decimal number are evaluated as that decimal in double precision, other values (more digits, tiny, huge) are used exactly. Without this 7 of the 34 files differed in the sixth decimal after 6-8 iterations.
Regenerated/deleted goldens: no golden was regenerated; `solver/legacy__parametricTree2.l.d1..d3` were deleted (#14: the rule `A` of that file contains `[^+a)`, the legacy output froze a stray `)`; the rewriter reports the rule). `d0` of that file and the other 160 goldens are unchanged. The shipped file itself is untouched (`Resources/` is not T04's), so `tree file legacy/parametricTree2.l` now throws a `RewriteError` (T07: catch it in the console command; the likely fix of the file is `[^(a)`).
Observable changes for the engine: the product string is canonical (`F(2.000000)` also for literal `F(2)` and for the axiom at depth 0; the interpreter parses numbers, so this is harmless); an unused broken rule is not reported until it becomes applicable (`initialDepth <= iteration`); `A(1)` rewritten by a parameterless rule `A` used to drop the `(1)` silently and is now an arity error.
Why: Review Focus 3, 4, 5 and the Linux requirement (the regex solver loses the tail of every production on libstdc++); the global rule that goldens stay identical unless a listed bug is hit.
Consequences / alternatives rejected: comparing goldens with a numeric tolerance (rejected: hides real regressions) and regenerating the 7 affected goldens (rejected: unnecessary churn once the six-decimal model is kept). The six-decimal rounding is a deliberate legacy-compatibility device; a later task may drop it (and regenerate the goldens with a DECISIONS entry) once nobody depends on digit-identical products.

## D-015 — treegen geometry: exact sizing, skipped degenerate segments, bit-identical threads (2026-10-25, T06)
Decision: `treegen::buildGeometry(skeleton, params, {ringDensity, seed, threads})` (`Geometry.h`, `MeshData.h`) and the facade `generateTree` (`TreeGenerator.h`, the only header a consumer needs) replace `LindenmayerTreeMeshGenerator` and the leaf loop of `LindenmayerTree::generateInstancedLeaves` (T07 switches the engine over). The ring math is the legacy one operation for operation (ring point `(radius*cos/2, 0, radius*sin/2)`, `radius` is a DIAMETER, last ring vertex repeats the first for the UV seam, `u = j/(ringDensity-1)`, `v` 0 bottom / 1 top, radial normal from the frame's 3x3, 6 indices per quad in the legacy order, root emits nothing). The frozen reference `tests/treegen/legacy_reference/LegacyGeometryReference.h` (deleted in T07) reproduces the legacy code; positions, normals and UVs of five shipped rule files and a hand-written production match it (measured deviation 0 on MSVC /O2, tolerance 1e-4) and the indices are identical.
Intentional differences from the legacy generator:
1. **Exact sizes, `uint32_t` indices, no caps.** `2*ringDensity` vertices and `6*(ringDensity-1)` indices per emitted segment, computed before filling (the engine's 100 000 vertex / 4 000 000 index buffers are gone: depth 10 of `parametricTernaryTreeE.json` is 2.1 M vertices / 5.7 M indices). More than 2^32-1 vertices or `ringDensity < 3` throws `treegen::Error`.
2. **Degenerate segments are skipped, not drawn as NaN.** A segment is skipped (no vertices, no indices) when its own or its parent's radius is `<= 0`, or when its own or its parent's radius, roll or frame is NaN/Inf, beyond 1e8, or singular (x and z axes parallel); counted in `TreeGeometry::stats` (`skippedZeroRadius`, `skippedInvalidFrame`). A finite non-zero frame whose normal would underflow falls back to the local radial direction. The mesh never contains NaN/Inf; the legacy code produced NaN normals for radius 0 (Review Focus 5).
3. **Threads.** The vertex computation is split into contiguous chunks of segments with `std::thread` only above 50 000 vertices (`threads = 0`), `GeometryOptions::threads` forces 1 or n threads. Every vertex is a pure function of its segment, so the result is bit-identical for every thread count (tested 1/2/3/4/7/64 and automatic). The Boost thread group and its `hardware_concurrency()`-way split (which also ran for 10 vertices) are gone; treegen links `Threads::Threads`.
4. **Leaves from `Rng(seed).derive(3)`**: one draw per tip (`u <= leafGrowthProb` keeps it), a second one for the rotation about Y in `[-d, d]` when `leavesAngleDiversity > 0`; `leaf = segment.model * rotation` without the tree's world transform (the engine multiplies it). The legacy loop used a Boost generator seeded with `time(0)`. `leafGrowthProb <= 0` (or NaN) gives no leaves. The root is a tip when the skeleton has no segments, as in the legacy loop. A kept leaf with a non-finite transform is dropped and counted (`skippedLeaves`) after its draws.
5. **`F(1)` is 18 vertices and 48 indices** (16 triangles); the T06 brief's "24 indices" was a typo.
Additive API beyond the T03-T05 design text: `GeometryOptions::threads`, `GenerateOptions::threads`, `GeometryStats`, `TreeGeometry::stats` (documented in `treegen-design.md`). `generateTree` passes one seed (`options.seed`, or `params.seed` when 0) to all three stages; they derive streams 1/2/3 from it themselves.
Why: Review Focus 5 (geometry half), the "growth" focus (fixed GL buffer capacities) and the determinism rule (no time-seeded RNGs, thread-count independent output).
Consequences: T07 must size the GL buffers from `trunk.vertices.size()` / `trunk.indices.size()` (convert `uint32_t` to `int` indices only below 2^31), recreate them per generated tree and keep the Boost-free build. Trees with a zero-radius segment (`=(0)`) lose that segment's triangles; before they showed black NaN artefacts.
